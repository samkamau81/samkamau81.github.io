2026 · Peak Power — Data Center Planning & Operations Simulator
⚡

Overview:
A browser-based planning tool for evaluating a 75 MW data center campus before capital is committed. It brings site screening, project timelines, power and finance planning, plant performance, and hour-by-hour operations into one interactive prototype.

What it does:
Compares project scenarios and screens 3,142 U.S. counties across nine dimensions: location, energy, policy, fiber, land, grid reliability, water, natural hazard, and time to power. Energy dispatch modeling is limited to ERCOT (Texas); counties elsewhere receive rule-based screening rather than an hourly energy simulation.

Engineering:
Built as a static application with plain HTML, CSS, and JavaScript, with no framework or build step. Its deterministic dispatch and accounting engine models 87,600 hourly steps across ten years, using an 8,760-hour reference year repeated annually. It compares 384 pre-simulated power plans and re-simulates plans when selected assumptions change. The interface includes portfolio/timeline views, a county finder, finance and energy controls, plant performance, and live operations.

Data and methods:
Uses a symposium packet for hourly energy inputs, alongside public data including U.S. Census county boundaries, WRI Aqueduct water stress, FEMA hazard data, LBNL interconnection queue data, CAIDA network-facility locations, EIA power-plant data, and OpenStreetMap-derived data center locations. Grades and business inputs are explicitly treated as screening assumptions.

Recognition: Winning project at Columbia University's Grid Tech 2026 Symposium (as stated in the supplied project brief).

Results and limits:
The prototype produces comparative scenario estimates; its documentation says these are not quotes or guarantees and notes that the model is not calibrated against real outcomes. Individual team responsibilities are not documented in the accessible project files.

Source: GitHub repository

2026 · Spot it, sort it — Viam Robotic Vision Language Action Model for Defect Detection.
🤖

Overview:
A defect-inspection and sorting prototype for parts on a plain inspection surface. It combines camera-based part localization, anomaly scoring, per-item decisions and logging, with a Viam-connected robot workflow.

Architecture:
A wrist-mounted RealSense camera feeds a PatchCore model from Anomalib, compiled with OpenVINO on the Intel NUC. The Viam vision module locates parts against the background, scores anomaly heat over each part relative to the same frame’s surface, and labels it normal, anomalous, or hold. Decisions are logged before the arm workflow; depth and camera geometry support grasp planning.

Model experiments:
The repository also contains an OpenVINO GenAI vision-language-model path and a YOLO classifier experiment. The handoff documentation says the live judging setup used PatchCore for decisions; YOLO was measured on the NPU but not used to decide. The VLM was an exploratory path, not the verified deployed decision-maker.

Reported result:
In the documented blind test on seven defective shots, PatchCore caught 6/7 (including three foreign blocks), while supervised YOLO caught 2/7. This is a small, setup-specific test, not a general performance guarantee. The notes also record sensitivity to lighting and background changes.

Robot integration status:
The Viam modules include per-item logging and a depth-based grasp planner. Handoff notes say real picks were not verified; the later sorter was left in dry-run with motion blocked pending station checks. The repository does not establish a successful autonomous sorting run.

Technologies: Python 3.12, Viam SDK and modules, Anomalib PatchCore, OpenVINO, OpenCV, NumPy, depth-camera geometry, pytest.

Personal contribution: The accessible documentation describes team implementation but does not identify individual responsibilities; your specific contribution needs confirmation.

Source: GitHub repository

2025–26 · Golden Record (National Data Integrity System)

Purpose:
The National Data Integrity System (NDIS) prototype helps Kenya’s Ministry of Education find duplicate and inconsistent learner records, so officials can make better-informed education and funding decisions.

My role:
AI/software engineer and Kenya prototype lead. I worked with Ministry staff through discovery, experimentation, two-week build sprints, and review sessions, turning data-quality needs into a testable matching and reporting workflow.

Matching approach:
Compared records with phonetic name matching and weighted field-level similarity. Ministry data officers helped set which fields mattered most; the system flags candidate matches while officers make the final merge-or-keep decision. This human review step keeps the system from treating uncertain matches as fact.

Data and outputs:
Because access to production records was unavailable during the challenge, we co-developed realistic synthetic data with Ministry staff. Cleaned records feed plain-language executive summaries for officials. The case study describes the prototype as substantially faster than manual work, but does not publish a numerical benchmark or evidence of a production rollout.

Technical focus: Record linkage, phonetic matching, classical machine learning, synthetic data, human-in-the-loop validation, and language-model-assisted reporting.

Case study: NDIS and the Kenya prototype

2024 · Delta Laser Weeding Robot (Computer Vision & Robotics Backend)

Overview:
An edge-computer-vision and robotics project for locating weeds and translating detections into targeted laser-weeding actions. The system is designed around a Delta robot, with inference running on a Raspberry Pi 4 rather than requiring a desktop GPU.

2023 · MentalMuse (NLP Mental Health Analysis)

Overview:
A questionnaire-based mental-wellness prototype that combines multilingual sentiment analysis with a directory of local support resources. It is an exploratory self-assessment experience, not a clinical diagnosis.

Analysis flow:
Users respond to weighted questions; a multilingual BERT sentiment model scores each response, and the app combines the scores into an estimated stress-level percentage. It then queries Snowflake for relevant psychologist or psychiatrist information, including location and available guidance, based on the user’s county. The repository describes database tables for provider offices, reviews, and advice, so the result connects the questionnaire output to local support information rather than ending at a sentiment score.

Engineering:
Built the application in Streamlit, connected Python workflows to Snowflake through Snowpark, and integrated the Transformers/PyTorch sentiment model with the resource lookup. This connects free-text analysis, weighted questionnaire logic, and location-aware database queries in a single app.

Technologies: Python, Streamlit, Snowflake/Snowpark, Transformers, PyTorch, and multilingual BERT sentiment analysis.

Demo and source: MentalMuse demo · GitHub repository. The repository does not document clinical validation or model-accuracy benchmarks.
